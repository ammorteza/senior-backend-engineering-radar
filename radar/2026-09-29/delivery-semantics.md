## What it is

Delivery semantics describe what happens to a message across attempts, acknowledgements and failures. At-most-once permits loss but avoids broker redelivery within its stated scope. At-least-once permits repeated delivery while attempting to preserve work. Exactly-once guarantees require a specific definition of what is counted and where the guarantee applies.

Separate publishing, delivery, application execution and durable business effects. A publisher can submit the same logical event twice, a broker can redeliver one message, and a consumer can repeat a database update. Those are different duplication boundaries; one configuration cannot automatically cover all three.

## Why it matters for backend engineers

A consumer usually changes something outside the broker. If its database commit succeeds and the process crashes before acknowledging, the next worker cannot infer that success from the broker's delivery state alone. A duplicate is a normal consequence of uncertainty, not necessarily an infrastructure defect.

Conversely, acknowledging first creates a window in which the broker considers work complete although the application has not persisted it. Engineers must choose the acceptable failure behavior from the effect being protected, then make the acknowledgement point consistent with that choice.

## How it works

Under a typical at-least-once protocol, the broker retains responsibility until a subscriber acknowledges. Delivery may be protected by a lease or acknowledgement deadline; expiration allows another attempt. Extending that deadline reduces unnecessary overlap but does not make the worker's external operations transactional.

For a database-only consumer, a useful boundary is one transaction containing both a unique processed-event record and the business update. On redelivery, the committed record proves that the update already happened. If that transaction rolls back, neither the marker nor the change remains. Acknowledge only after commit or after confirming an earlier committed result.

An external API cannot ordinarily join that transaction. Its own operation identity, duplicate-safe request contract and outcome lookup must close the remaining uncertainty. If those mechanisms are absent, the design needs explicit reconciliation or must accept a stated risk of loss or duplication.

Broker transactions can coordinate the operations that participate in their protocol. For example, Kafka can commit produced records and consumed offsets together for an appropriate consume-transform-produce workflow. That does not include an unrelated database merely because the consumer also writes to it.

## Key concepts

**Attempt versus event identity.** Redelivery should retain a stable logical identity even if receipt handles or acknowledgement tokens change. Use the identity appropriate to the protected effect, not a fresh ID generated by each worker.

**Acknowledged versus completed.** Acknowledgement is a broker decision. Business completion may require a durable local result, a confirmed remote action or a later workflow step.

**Ordering versus duplication.** Removing repeats does not put different messages in order. Applying version 8 twice safely says nothing about whether version 7 may overwrite it afterward.

**Quarantine versus recovery.** A dead-letter destination isolates work that cannot currently progress. It does not resolve that work or ensure anybody will examine it. Retain enough context to repair and replay deliberately.

**Retention limits the promise.** “At least once” is not a guarantee of eventual success despite expired retention, deleted subscriptions or permanent application failure. State operational assumptions alongside the delivery label.

## Production example

A document-indexing worker receives event `E42` for document version 9. It must update a local searchable representation and record processing progress. Consider three crash points:

| Crash point | Durable state | Safe recovery |
| --- | --- | --- |
| Before database commit | Neither update nor marker exists | Redelivery executes the transaction |
| After commit, before acknowledgement | Update and marker both exist | Redelivery recognizes the committed event |
| After acknowledgement | Committed result exists | Normal processing advances |

The unique key is scoped to this consumer and event identity. A single global marker shared by unrelated consumers would incorrectly let one consumer suppress another's work. Concurrent attempts must contend on a database constraint or equivalent atomic mechanism, rather than both passing a preliminary existence check.

The worker also rejects obsolete document versions under its update rule. Deduplicating `E42` alone cannot stop a distinct older event from regressing the representation. Tests therefore include the same event twice, simultaneous attempts, version 8 after version 9, and a crash after commit.

If the representation lives in a separate search service, this local transaction no longer covers it. The search write needs an appropriate stable document key and version condition, or another durable publication/recovery protocol. The table describes one database boundary, not a universal cross-system solution.

## Trade-offs

At-most-once can suit disposable observations where a missing sample is preferable to retry overhead. It is inappropriate when silent loss breaks the product. At-least-once usually makes durable work easier to recover, but requires duplicate handling and capacity for retries.

Transactions reduce ambiguity among their participants at the cost of coordination and coupling. Evaluate that benefit against the actual workflow; stronger broker semantics may simplify one stage without eliminating the harder external boundary.

## Failure modes / pitfalls

A deduplication marker committed before the business update can lose work; committed afterward in another transaction, it can permit repeats. In-memory markers disappear on restart and do not coordinate workers.

Unlimited retries can let one poison message consume capacity indefinitely. Skipping it can also violate an ordered workflow. Define whether later work for that entity pauses, proceeds independently or waits for repair, and make that state visible.

## When to use it

Choose delivery semantics whenever adding a producer, worker or asynchronous integration. Document the protected effect, commit point, replay window and response to permanent failure.

Use failure injection around those commit points to check the claimed behavior. Happy-path throughput does not establish a delivery guarantee.

## When not to use it

Do not pay for a stronger broker feature solely to obtain a reassuring label. First determine whether it covers the operation that can cause harm.

Do not discard documented exactly-once mechanisms either: they can remove substantial duplicate-processing work within their supported scope. Combine them with the remaining application protections.

## What a Senior Engineer should know

A Senior Engineer should trace a message from publication through durable processing and acknowledgement, naming every uncertainty window. They should implement concurrent duplicate handling and distinguish redelivery from publisher-generated duplicates.

They should explain what happens when retries expire, an ordered message is quarantined, or a consumer restarts after committing its effect.

## What a Staff Engineer should understand

A Staff Engineer should turn delivery labels into explicit product guarantees across service owners. Establish who owns unresolved work, retention changes and replay authorization, especially when several teams participate in one outcome.

Review guarantees against recovery procedures as well as normal traffic. A manual replay months later must not silently bypass the identities and boundaries that make live processing safe.
