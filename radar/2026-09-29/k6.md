## What it is

k6 is a programmable load-testing tool in which scripts define user behavior, scenarios, checks, and thresholds. It can model both virtual-user-driven workloads and arrival-rate workloads.

The executor choice matters. A fixed number of virtual users naturally slows its request arrival when the service slows. An arrival-rate executor attempts to start iterations at the configured rate, which is more appropriate when real traffic arrives independently of server response time.

## Why it matters for backend engineers

A load tool can create misleading confidence if it generates the wrong traffic. If a service becomes slower and the test automatically sends fewer requests, apparent stability may simply be coordinated omission.

k6 also needs enough virtual users and generator resources to sustain an arrival-rate scenario. Dropped iterations can mean the configured rate was never achieved.

## How it works

A k6 script imports protocol clients, defines functions representing operations, and configures `options.scenarios`. Each scenario selects an executor and can have separate environment/tag configuration.

Closed-model executors run iterations from a bounded virtual-user population. Arrival-rate executors schedule iteration starts independently of completion and allocate VUs as needed up to configured limits.

**Checks** record correctness observations such as status and response fields. A failing check does not automatically fail the test. **Thresholds** define pass/fail criteria on metrics, for example request failure rate below 1% and p95 latency below 300 ms.

Custom metrics can record application-specific outcomes such as accepted jobs or business validation failures. Tags help segment results but should use bounded values; raw IDs create high cardinality.

## Key concepts

**Iteration versus request.** One iteration can contain login, several API calls, sleeps, and cleanup. Arrival rate of iterations is not necessarily HTTP request rate.

**preAllocatedVUs/maxVUs.** Arrival-rate scenarios need enough VUs to keep starting iterations while previous ones remain in flight.

**Dropped iterations.** Requested iterations that could not start. Investigate generator/VU capacity rather than excluding them from results.

**Checks versus thresholds.** Checks measure correctness; thresholds decide test success.

**Setup/teardown.** Useful for controlled fixture creation but should not hide expensive production behavior from the measured scenario.

## Production example

A report-submission API must accept 200 jobs per second while p95 submission latency remains under 250 ms and fewer than 0.5% of valid requests fail.

A closed 100-VU test appears healthy, but when latency increases, users complete iterations more slowly and request rate falls below the production arrival rate.

The team switches to a constant-arrival-rate scenario at 200 iterations per second and preallocates enough VUs based on observed iteration duration. It uses realistic authentication and report-size distributions.

Checks verify that successful responses include a valid job ID and that validation errors occur only for deliberately invalid inputs. Thresholds cover `http_req_failed`, p95 latency, and a custom business-success metric.

During one run, `dropped_iterations` rises. The target remains underutilized; the generator lacks enough VUs. The team fixes generator configuration before drawing a capacity conclusion.

Target telemetry—CPU, database pool wait, queue age—is captured beside k6 metrics so the result identifies the bottleneck rather than only latency.

## Trade-offs

k6 scripts are versionable and easy to automate. They still produce synthetic traffic: realism depends on the script, dataset, environment, and generator capacity.

Arrival-rate tests expose overload more directly but require careful VU sizing. Closed models can be more natural for a fixed population of interactive users.

## Failure modes / pitfalls

Testing only one happy-path payload hides expensive branches. Reusing one user or tenant can create unrealistic cache locality or contention.

A generator saturated on CPU/network can make the target look incapable of more traffic. Successful HTTP status alone does not prove correct business output.

Running uncontrolled load against production or shared downstream providers can trigger quotas or incidents.

## When to use it

Use k6 for repeatable API load, stress, and soak tests, performance regression checks, and capacity experiments whose workload can be modeled in scripts.

Version the workload and acceptance thresholds alongside the service where practical.

## When not to use it

Do not treat one short k6 run as a permanent capacity certificate. Do not select an executor without understanding how it shapes arrivals.

For browser-rendering performance or kernel-level microbenchmarks, use tools designed for those questions instead.

## What a Senior Engineer should know

A Senior Engineer should choose closed versus arrival-rate executors, size VUs, define checks and thresholds, use realistic data, and monitor dropped iterations.

They should correlate k6 results with target-system saturation and verify the load generator itself remains healthy.

## What a Staff Engineer should understand

A Staff Engineer should define safe performance environments, representative scenario libraries, data handling, and organization-wide acceptance evidence.

They should prevent teams from comparing unrelated workloads by one headline RPS number.
