## What it is

An operation is idempotent when repeating it has the same intended effect as performing it once. In backend systems, idempotency is a practical technique for making retries and duplicate message delivery safe.

It does not necessarily mean executing the code only once; it means repeated execution does not create unintended additional effects.

## Why it matters for backend engineers

Networks and message brokers cannot give applications perfect knowledge about whether an operation happened. Retries are therefore necessary, and retries create duplicates.

Payments, order creation, notifications, inventory changes and asynchronous consumers all need explicit duplicate handling when repeated effects would be harmful.

## How it works

A caller can attach an idempotency key representing one logical operation. The receiving service stores the key together with the durable outcome. A retry with the same key returns or reuses that outcome instead of performing the side effect again.

Consumers can similarly persist processed event identifiers or design state transitions so reapplying an event is naturally harmless.

The deduplication record must be committed at the correct atomic boundary with the business change; otherwise a crash can separate "processed" from the actual side effect.

## Key concepts

### Idempotency key
A stable identifier for one logical request, normally generated by the caller.

### Deduplication boundary
The component responsible for deciding whether two attempts represent the same operation.

### Atomicity
Recording the key and changing business state often need one transaction.

### Retention window
Deduplication state cannot always be retained forever. Expiration must match realistic retry and replay behavior.

### Naturally idempotent operations
Setting status to cancelled can be idempotent; incrementing balance by 10 usually is not without additional identity.

## Production example

A checkout client sends CreatePayment with an idempotency key. The payment service charges the provider and commits the payment, but the response is lost.

The client retries. Instead of creating another charge, the service finds the existing key and returns the original payment result.

For external providers, the same logical operation key should be propagated under their documented idempotency contract. A local transaction cannot atomically include an arbitrary provider call: persist the operation claim before calling, and use provider lookup or duplicate-safe retry to resolve a crash or timeout before the local result is recorded. If the same key arrives with a different payload, reject it rather than silently returning an unrelated result.

## Trade-offs

Idempotency adds storage, lookup cost, lifecycle management and concurrency handling. Weakly designed deduplication can itself become a bottleneck.

However, this cost is often much lower than trying to prevent retries or manually reconcile duplicate financial and business effects.

## Failure modes / pitfalls

Mistakes include generating a new key on every retry, storing deduplication state after the side effect, using keys with ambiguous scope, expiring records too quickly and treating duplicate messages as exceptional rather than expected.

Concurrent requests with the same key require synchronization; two workers must not both observe "not processed" and execute the side effect.

## When to use it

Use idempotency for retryable commands with nontrivial side effects, asynchronous consumers, payment operations and workflows where clients may repeat requests after ambiguous failures.

## When not to use it

Do not add a heavyweight deduplication store to operations that are already naturally idempotent and cheap. Also do not confuse idempotency with exactly-once execution.

## What a Senior Engineer should know

A Senior Engineer should identify where duplicates can arise, choose the idempotency boundary, design stable keys and make deduplication atomic with state changes.

They should assume at-least-once delivery can produce duplicates.

## What a Staff Engineer should understand

A Staff Engineer should define idempotency across service boundaries and long-running workflows, including retention, replay and external providers. They should establish consistent API conventions and understand where end-to-end guarantees break.

They should prefer architectures where correctness remains robust under retry rather than depending on infrastructure claims of exactly-once execution.
